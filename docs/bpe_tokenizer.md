## 2 字节对编码（BPE）分词器

在本作业的第一部分，我们将训练并实现一个字节级字节对编码（BPE）分词器 [Sennrich et al., 2016, Wang et al., 2019]。具体来说，我们将任意（Unicode）字符串表示为字节序列，并在此字节序列上训练 BPE 分词器。之后，我们将使用这个分词器将文本（字符串）编码为 token（整数序列），用于语言建模。

---

## 2.1 Unicode 标准

Unicode 是一种文本编码标准，将字符映射到整数码点（code points）。截至 Unicode 16.0（2024年9月发布），该标准定义了 168 种文字中的 154,998 个字符。例如，字符 "s" 的码点为 115（通常记作 U+0073，其中 U+ 是约定前缀，0073 是 115 的十六进制表示），字符 "ŷ" 的码点为 29275。在 Python 中，可以使用 `ord()` 函数将单个 Unicode 字符转换为其整数表示，`chr()` 函数则将整数 Unicode 码点转换为对应字符的字符串。

```python
>>> ord('ŷ')
29275
>>> chr(29275)
'ŷ'
```

> **目的与价值**：Unicode 是现代文本处理的基础。理解"字符"（抽象符号）与"码点"（整数）的区分，是理解后续编码转换的前提。`ord` 和 `chr` 是 Python 中最基础的字符←→整数转换工具。

## 2.2 Unicode 编码

虽然 Unicode 标准定义了字符到码点（整数）的映射，但直接在 Unicode 码点上训练分词器是不切实际的——词汇表会过于庞大（约 150K 项）且稀疏（许多字符极少使用）。因此，我们将使用一种 **Unicode 编码**，将 Unicode 字符转换为字节序列。Unicode 标准本身定义了三种编码：UTF-8、UTF-16 和 UTF-32，其中 UTF-8 是互联网上占主导地位的编码（超过 98% 的网页使用）。

在 Python 中，使用 `encode()` 函数可以将 Unicode 字符串编码为 UTF-8，通过迭代（如调用 `list()`）可以访问 Python `bytes` 对象的底层字节值，使用 `decode()` 函数可以将 UTF-8 字节字符串解码回 Unicode 字符串。

```python
>>> test_string = "hello! こんにちは!"
>>> utf8_encoded = test_string.encode("utf-8")
>>> print(utf8_encoded)
b'hello! \xe3\x81\x93\xe3\x82\x93\xe3\x81\xab\xe3\x81\xa1\xe3\x81\xaf!'
>>> print(type(utf8_encoded))
<class 'bytes'>
>>> # 获取编码字符串的字节值（0到255的整数）
>>> list(utf8_encoded)
[104, 101, 108, 108, 111, 33, 32, 227, 129, 147, 227, 130, 147, 227, 129, 171, 227, 129,
161, 227, 129, 175, 33]
>>> # 一个字节不一定对应一个 Unicode 字符！
>>> print(len(test_string))
13
>>> print(len(utf8_encoded))
23
>>> print(utf8_encoded.decode("utf-8"))
hello! こんにちは!
```

通过将 Unicode 码点转换为字节序列（如通过 UTF-8 编码），我们本质上是将码点序列（范围 0 到 154,997 的整数）转换为字节值序列（范围 0 到 255 的整数）。**256 长度的字节词汇表**处理起来更加方便。使用字节级分词时，我们不必担心未登录词（out-of-vocabulary）问题，因为任何输入文本都可以表示为 0 到 255 的整数序列。

> **目的与价值**：这里揭示了为什么用字节做分词基础词汇：256 个字节值覆盖了所有可能的输入，永远不会遇到未知 token。相比之下，字符级词汇需要 150K+ 项，词级词汇则需要数十万项且仍有未登录词问题。UTF-8 的聪明之处在于：ASCII 字符（英文字母、数字、标点）只用 1 个字节，而其他语言的字符用 2-4 个字节——这使得英文主导的语料处理更高效。

## 2.3 子词分词（Subword Tokenization）

虽然字节级分词可以解决词级分词器面临的未登录词问题，但将文本分词为字节会导致输入序列极长。这会减慢模型训练速度——10 个词的句子在词级语言模型中可能只有 10 个 token，但在字符级模型中可能有 50 个或更多（取决于词的长度）。处理这些更长的序列在模型的每一步都需要更多计算。此外，在字节序列上进行语言建模很困难，因为更长的输入序列在数据中产生了更长的长程依赖。

**子词分词**（Subword Tokenization）是词级分词器和字节级分词器之间的折中方案。字节级分词器的词汇表有 256 个条目（字节值为 0 到 255）。子词分词器以更大的词汇表为代价，换取对输入字节序列更好的压缩。例如，如果字节序列 `b'the'` 在我们的原始训练数据中频繁出现，将其作为词汇表中的一个条目，就可以把这个 3-token 序列压缩为单个 token。

我们如何选择要添加到词汇表的子词单元？Sennrich et al. [2016] 提出使用**字节对编码**（BPE；Gage, 1994），这是一种压缩算法，迭代地将最频繁的字节对替换（"合并"）为单个新的未使用索引。注意，该算法向词汇表添加子词 token 以最大化对输入序列的压缩——如果一个词在输入文本中出现足够多次，它将被表示为单个子词单元。

使用 BPE 构建词汇表的子词分词器通常被称为 **BPE 分词器**。在本作业中，我们将实现一个**字节级 BPE 分词器**，其词汇表项是字节或字节的合并序列，这样我们可以兼顾未登录词处理和可管理的输入序列长度。构建 BPE 分词器词汇表的过程称为"训练" BPE 分词器。

> **目的与价值**：BPE 是现代 LLM（GPT、LLaMA 等）使用的分词方法的核心。它的精妙之处在于：不需要任何语言学知识，只需统计字节对的频率，就能自动学到有意义的子词单元（如英文中的 "ing"、"tion"，或中文中常见的字组）。"字节级"意味着词汇表从 256 个单字节开始，任何语言都能处理，不会有未登录词。

## 2.4 BPE 分词器训练

BPE 分词器的训练过程包含三个主要步骤。

### 词汇表初始化（Vocabulary Initialization）

分词器词汇表是字节串 token 到整数 ID 的一一映射。由于我们在训练字节级 BPE 分词器，初始词汇表就是所有字节的集合。由于有 256 个可能的字节值，初始词汇表大小为 256。

### 预分词（Pre-tokenization）

有了词汇表，理论上可以直接统计字节在文本中相邻出现的频率，并从最频繁的字节对开始合并。然而，这在计算上代价极高，因为每次合并都需要对整个语料库做完整扫描。此外，直接跨语料库合并字节可能产生仅在标点符号上有差异的 token（如 `dog!` 和 `dog.`），即使它们在语义上高度相似，也会获得完全不同的 token ID。

为了避免这种情况，我们对语料库进行**预分词**。可以将其理解为对语料库的粗粒度分词，帮助我们统计字符对出现的频率。例如，单词 `'text'` 可能作为预 token 出现 10 次。在这种情况下，当我们统计字符 `'t'` 和 `'e'` 相邻出现的频率时，我们知道 `'text'` 中有 `'t'` 和 `'e'` 相邻，可以将其计数增加 10，而无需遍历整个语料库。由于我们在训练字节级 BPE 模型，每个预 token 被表示为 UTF-8 字节序列。

Sennrich et al. [2016] 的原始 BPE 实现通过简单地按空格分割（`s.split(" ")`）来进行预分词。相比之下，我们将使用基于正则表达式的预分词器（GPT-2 使用的方式；Radford et al., 2019），来自 [github.com/openai/tiktoken](https://github.com/openai/tiktoken/pull/234/files)：

```python
>>> PAT = r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""
```

交互式地用这个预分词器分割一些文本，有助于更好地理解其行为：

```python
>>> # 需要 `regex` 包
>>> import regex as re
>>> re.findall(PAT, "some text that i'll pre-tokenize")
['some', ' text', ' that', ' i', "'ll", ' pre', '-', 'tokenize']
```

> **目的与价值**：预分词的意义是**防止跨词边界合并**。没有预分词，BPE 可能会把 `"dog."` 中的 `"g."` 合并成一个 token，但这个 token 在其他语境（如 `"big."`) 中意义完全不同。GPT-2 的正则表达式把文本智能地切成语言单元（缩略词、字母序列、数字序列、标点等），确保合并只在同类字符内发生。

在代码中，应该使用 `re.finditer` 而非 `re.findall`，以避免在构建预 token 到计数映射时将预分词结果全部存储在内存中。

### 计算 BPE 合并（Compute BPE Merges）

将输入文本转换为预 token 并用 UTF-8 字节表示每个预 token 后，就可以计算 BPE 合并（即训练 BPE 分词器）。

从高层来看，BPE 算法**迭代地统计每对字节**，找出频率最高的对 `("A", "B")`，然后将每次出现的 `("A", "B")` 合并为新 token `"AB"`。这个新合并的 token 被加入词汇表；因此，BPE 训练后的最终词汇表大小等于初始词汇表大小（本例为 256），加上训练期间执行的 BPE 合并操作次数。为了效率，BPE 训练期间不考虑跨预 token 边界的字节对。[^2]

计算合并时，**通过偏好字典序更大的对来决定性地打破平局**。例如，如果 `("A", "B")`、`("A", "C")`、`("B", "ZZ")` 和 `("BA", "A")` 都具有最高频率，我们会合并 `("BA", "A")`：

```python
>>> max([("A", "B"), ("A", "C"), ("B", "ZZ"), ("BA", "A")])
('BA', 'A')
```

[^2]: 注意，原始 BPE 公式 [Sennrich et al., 2016] 指定了包含词尾 token。在训练字节级 BPE 模型时，我们不添加词尾 token，因为所有字节（包括空格和标点符号）都包含在模型词汇表中。由于我们明确表示了空格和标点符号，学到的 BPE 合并将自然反映这些词边界。

### 特殊 token（Special Tokens）

通常，某些字符串（如 `<|endoftext|>`）用于编码元数据（如文档间的边界）。在编码文本时，通常希望将某些字符串视为"特殊 token"，永远不被拆分为多个 token（即始终保留为单个 token）。例如，序列结束字符串 `<|endoftext|>` 应始终保留为单个 token（即单个整数 ID），这样我们才知道何时停止语言模型的生成。这些特殊 token 必须被添加到词汇表，以便获得对应的固定 token ID。

### 示例 (bpe_example)：BPE 训练示例

以下是来自 Sennrich et al. [2016] 的一个示例。考虑由以下文本组成的语料库：

```
low low low low low
lower lower widest widest widest
newest newest newest newest newest newest
```

词汇表有一个特殊 token `<|endoftext|>`。

**词汇表初始化**：我们用特殊 token `<|endoftext|>` 和 256 个字节值初始化词汇表。

**预分词**：为了简化并专注于合并过程，本例假设预分词就是按空格分割。预分词并计数后，我们得到频率表：

```
{low: 5, lower: 2, widest: 3, newest: 6}
```

将此表示为 `dict[tuple[bytes], int]`，例如 `{(l, o, w): 5 …}`。注意，即使是单个字节，在 Python 中也是 `bytes` 对象。Python 中没有 `byte` 类型来表示单个字节，就像没有 `char` 类型来表示单个字符一样。

**合并过程**：首先统计每对连续字节，并求出它们出现的词的频率之和：`{lo: 7, ow: 7, we: 8, er: 2, wi: 3, id: 3, de: 3, es: 9, st: 9, ne: 6, ew: 6}`。对 `'es'` 和 `'st'` 平局，取字典序更大的 `'st'`。合并后得到 `{(l,o,w): 5, (l,o,w,e,r): 2, (w,i,d,e,st): 3, (n,e,w,e,st): 6}`。

第二轮中，`(e, st)` 是最常见的对（频率 9），合并得到 `{(l,o,w): 5, (l,o,w,e,r): 2, (w,i,d,est): 3, (n,e,w,est): 6}`。如此继续，最终得到合并序列：`['s t', 'e st', 'o w', 'l ow', 'w est', 'n e', 'ne west', 'w i', 'wi d', 'wid est', 'low e', 'lowe r']`。

取前 6 次合并：`['s t', 'e st', 'o w', 'l ow', 'w est', 'n e']`，词汇表元素为 `[<|endoftext|>, [...256字节字符], st, est, ow, low, west, ne]`。用这个词汇表和合并规则，`newest` 会被分词为 `[ne, west]`。

> **目的与价值**：这个例子直观地展示了 BPE 如何学到有意义的子词单元。`'st'`、`'est'`、`'ow'` 等都是英语中的常见子词，BPE 通过纯统计方法自动发现了它们。注意 `newest → [ne, west]` 而非 `[new, est]`——BPE 的结果取决于语料中的频率，不总是语言学上"正确"的切分，但这通常对语言模型没有影响。

### 并行化预分词（Parallelizing Pre-tokenization）

你会发现预分词步骤是主要瓶颈。可以使用内置库 `multiprocessing` 并行化代码来加速预分词。具体来说，我们建议在并行实现中，在确保块边界出现在特殊 token 开头的同时对语料库进行分块。你可以直接使用以下链接中的起始代码来获取块边界，然后在各进程间分配工作：

这种分块始终是有效的，因为我们永远不希望跨文档边界合并。出于作业目的，你可以始终以这种方式分割。不必担心收到不含 `<|endoftext|>` 的超大语料库的边缘情况。

### 预分词前移除特殊 token

在使用正则表达式模式（`re.finditer`）运行预分词之前，应该从语料库（或并行实现中的块）中去除所有特殊 token。确保在特殊 token 上分割，使得不会在它们划定的文本边界处发生合并。例如，如果语料库（或块）是 `[Doc 1]<|endoftext|>[Doc 2]`，应该在特殊 token `<|endoftext|>` 处分割，分别对 `[Doc 1]` 和 `[Doc 2]` 进行预分词，避免跨文档边界合并。可以使用 `re.split` 以 `"|".join(special_tokens)` 作为分隔符（注意使用 `re.escape` 处理特殊 token 中可能出现的 `|`）。测试 `test_train_bpe_special_tokens` 将对此进行测试。

### 优化合并步骤（Optimizing the Merging Step）

上述示例中 BPE 训练的朴素实现很慢，因为每次合并都要遍历所有字节对来找出最频繁的对。然而，每次合并后只有与合并对重叠的那些对的计数会发生变化。因此，通过**索引所有对的计数**并**增量更新这些计数**，而非每次都显式遍历所有字节对，可以显著提升 BPE 训练速度。这种缓存策略可以带来显著加速，不过请注意，BPE 训练的合并部分在 Python 中是不可并行的。

> **目的与价值**：这是本作业最重要的性能优化点。朴素实现的复杂度是 $O(N \cdot V)$，其中 $N$ 是语料大小，$V$ 是合并次数。增量更新将每次合并的代价降低到只需更新受影响的对，实践中可以带来 10x 以上的加速。核心数据结构是一个维护 `pair → count` 的字典，以及一个反向索引 `pair → 包含该对的位置列表`。

**低资源技巧：性能分析（Profiling）**

应该使用 `cProfile` 或 `scalene` 等性能分析工具来识别实现中的瓶颈，并专注于优化这些部分。

**低资源技巧：降规模（Downscaling）**

建议不要一开始就在完整的 TinyStories 数据集上训练分词器，而是先在小的数据子集上训练——即"调试数据集"。例如，可以先在 TinyStories 验证集（22K 文档而非 2.12M）上训练分词器。这体现了一种通用策略：尽可能降规模以加速开发。选择调试数据集的大小或超参数配置需要仔细考量：调试集应该足够大，具有与完整配置相同的瓶颈（这样优化才能推广），但又不能大到运行很久。

## 2.6 BPE 分词器：编码与解码

在作业的上一部分，我们实现了在输入文本上训练 BPE 分词器的函数，得到了分词器词汇表和 BPE 合并列表。现在，我们将实现一个 BPE 分词器，加载给定的词汇表和合并列表，用它们将文本编码为 token ID 并将 token ID 解码回文本。

### 2.6.1 编码文本（Encoding Text）

用 BPE 编码文本的过程与训练 BPE 词汇表的过程相对应。主要有几个步骤。

**步骤 1：预分词**。首先对序列进行预分词，并将每个预 token 表示为 UTF-8 字节序列，与 BPE 训练时一样。我们将在每个预 token 内部将字节合并为词汇表元素，各预 token 独立处理（不跨预 token 边界合并）。

**步骤 2：应用合并规则**。然后按照 BPE 训练时创建的顺序，将词汇表元素合并序列应用到我们的预 token 上。

### 示例 (bpe_encoding)：BPE 编码示例

例如，假设输入字符串是 `'the cat ate'`，词汇表是 `{0: b' ', 1: b'a', 2: b'c', 3: b'e', 4: b'h', 5: b't', 6: b'th', 7: b' c', 8: b' a', 9: b'the', 10: b' at'}`，学到的合并为 `[(b't', b'h'), (b' ', b'c'), (b' ', b'a'), (b'th', b'e'), (b' a', b't')]`。

首先，预分词器将字符串分割为 `['the', ' cat', ' ate']`。然后，对每个预 token 应用 BPE 合并。

- 第一个预 token `'the'` 初始表示为 `[b't', b'h', b'e']`。查看合并列表，第一个适用的合并是 `(b't', b'h')`，将预 token 转换为 `[b'th', b'e']`。继续查找，下一个适用的合并是 `(b'th', b'e')`，转换为 `[b'the']`。再次查看，没有更多适用的合并，完成。对应整数序列为 `[9]`。
- 对剩余预 token 重复此过程：`' cat'` 应用合并后表示为 `[b' c', b'a', b't']`，整数序列为 `[7, 1, 5]`；`' ate'` 表示为 `[b' at', b'e']`，整数序列为 `[10, 3]`。
- 最终，编码输入字符串的结果为 `[9, 7, 1, 5, 10, 3]`。

**特殊 token**。你的分词器应能在编码文本时正确处理用户定义的特殊 token（在构造分词器时提供）。

**内存考虑**。假设我们想对一个无法装入内存的大型文本文件进行分词。为了高效地对这个大型文件（或任何其他数据流）进行分词，我们需要将其分成可管理的块并依次处理每个块，使内存复杂度为常数而非与文本大小线性相关。这样做时，我们需要确保 token 不跨块边界，否则会得到与对整个序列朴素分词不同的结果。

> **目的与价值**：BPE 编码的关键设计决策是**按合并创建顺序应用**，而非贪婪地总是选择最长匹配。这保证了编码的一致性——相同的文本总是产生相同的 token 序列。特殊 token 处理是实际系统中的重要细节，`<|endoftext|>` 必须作为整体保留。`encode_iterable` 是处理大文件的标准模式：生成器（`yield`）比返回列表更节省内存。

### 2.6.2 解码文本（Decoding Text）

要将整数 token ID 序列解码回原始文本，只需查找每个 ID 在词汇表中对应的条目（字节序列），将它们连接在一起，然后将字节解码为 Unicode 字符串。注意，输入 ID 不保证映射到有效的 Unicode 字符串（因为用户可以输入任意整数 ID 序列）。如果输入 token ID 不产生有效的 Unicode 字符串，应用官方 Unicode 替换字符 U+FFFD 替换格式错误的字节。`bytes.decode` 的 `errors` 参数控制如何处理 Unicode 解码错误，使用 `errors='replace'` 将自动用替换标记替换格式错误的数据。

## 章节总结

第 2 章构建了完整的 BPE 分词器管线。核心流程是：

```
原始文本
  ↓
预分词（GPT-2 正则表达式）
  ↓
UTF-8 字节表示
  ↓
BPE 合并训练（迭代合并最频繁字节对）
  ↓
词汇表 + 合并规则
  ↓
编码（文本 → token IDs）/ 解码（token IDs → 文本）
```

每个组件都有明确的设计动机：

| 组件 | 作用 |
|------|------|
| **Unicode / UTF-8** | 将任意文本统一为 0–255 的字节序列 |
| **预分词** | 防止跨词合并，保留语言学边界 |
| **BPE 合并** | 从频率统计中自动学习有意义的子词单元 |
| **特殊 token** | 处理元数据标记（文档边界等） |
| **增量更新** | 将合并步骤从 O(N·V) 加速到近似 O(N) |
| **encode_iterable** | 支持大文件的内存高效流式处理 |
